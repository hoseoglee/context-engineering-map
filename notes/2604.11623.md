# Context Kubernetes: Declarative Orchestration of Enterprise Knowledge for Agentic AI Systems (arXiv 2604.11623, v3 2026-04-16, Mouzouni — OPIT / Cohorte AI)

## 한 줄 요약
Kubernetes가 컨테이너를 오케스트레이션하듯, 조직 지식을 "올바른 에이전트에게, 올바른 권한·신선도·비용 한도 안에서" 전달하는 **선언형 컨텍스트 오케스트레이션 계층**을 제안한다. 6개 핵심 추상화 + YAML 매니페스트(Knowledge Architecture as Code) + reconciliation loop + "에이전트 권한 ⊂ 사람 권한" 3-tier 승인 모델이 핵심이며, 프로토타입(테스트 92개)과 8개 실험, TLA+ 모델체킹으로 검증했다.

## 문서가 제시하는 분류 체계 / 아키텍처
- **스케일링 시 반복되는 5대 문제** (에이전트 1개 → 2,000개로 갈 때)
  - Scheduling — 어떤 지식이 어떤 에이전트에게, 어떤 출처에서, 어떤 순서로 가나
  - Permissions — 에이전트가 읽기/쓰기/실행 가능한 범위와 사람 권한의 관계
  - Health monitoring — 받은 지식이 최신·완전·정확한가
  - State management — 지식의 버전·거버넌스·마이그레이션
  - Auditability — 누가, 언제, 어떤 에이전트로, 무엇에 접근했나
- **7개 요구사항 (NIST AI RMF 매핑)**
  - R1 Vendor Neutrality — 어떤 LLM/프레임워크/클라우드/데이터 소스와도 동작
  - R2 Declarative Management — 지식 아키텍처를 버전관리되는 기계가독 명세로
  - R3 Agent Permission Separation — 에이전트 권한은 사용자 권한의 엄격한 부분집합
  - R4 Context Freshness — TTL 초과 지식을 지속 감시·교정
  - R5 Intent-Based Access — "어디에 있는지"가 아니라 "무엇이 필요한지"로 요청, 토큰 예산 내 랭킹
  - R6 Complete Auditability — 모든 접근·행동·승인을 불변 로그로
  - R7 Organizational Intelligence — 에이전트 활동 집계에서 조직 지식 축적(권한 경계 유지)
- **6개 핵심 추상화**
  - Context Unit — 지식의 최소 주소 단위 (내용, 유형, 메타데이터, 버전, 임베딩, 허용 역할)
  - Context Domain — 격리 경계(네임스페이스), 소스·접근제어·신선도·라우팅·오퍼레이터·가드레일 묶음
  - Context Store — 실제 저장소(git, RDB, 외부 커넥터, 파일시스템)
  - Context Endpoint — 의도 기반 안정 인터페이스: 권한·신선도·토큰 예산 B 제약을 만족하는 unit 집합 반환
  - CxRI (Context Runtime Interface) — 저장소 어댑터 표준, 6개 연산(connect/query/read/write/subscribe/health); K8s CRI 대응
  - Context Operator — 도메인별 자율 컨트롤러(지식 인덱스 + LLM + 조직지능 모듈 + 가드레일)
- **7개 서비스 (시스템 아키텍처)**
  - Context Registry — 메타데이터 SSOT (etcd 대응)
  - Context Router — 의도 해석·라우팅·랭킹 (kube-scheduler + Ingress 대응)
  - Permission Engine — 3-tier 에이전트 권한 모델
  - Freshness Manager — fresh/stale/expired/conflicted 4상태 감시
  - Trust Policy Engine — 선언형 가드레일, 이상탐지, DLP, 감사 로그
  - Context Operators — 도메인 컨트롤러
  - LLM Gateway — 프롬프트 검사, 비용 계량
  - (+ Observability, Reconciliation Loop, Context API 10 endpoints: HTTPS+WSS+JWT)
- **3-tier 에이전트 승인 모델**
  - T1 Autonomous — 자유 실행 (컨텍스트 읽기, 초안 작성)
  - T2 Soft approval — 에이전트 UI에서 사용자 확인 (내부 메시지 전송)
  - T3 Strong approval — 에이전트가 읽기/쓰기 불가한 별도 채널 + 별도 인증요소 (계약 서명, 재무)
  - Excluded — 에이전트가 요청조차 불가 (직원 해고)
- **Reconciliation Loop의 drift 유형**: source disconnected / context stale / operator unhealthy / anomaly / reliability drift / permission change
- **Context Manifest 7개 섹션**: sources, access(roles·agentPermissions·crossDomain), freshness, routing(intentParsing·tokenBudget·priority 가중치), operator, trust(policies·anomalyDetection·audit), reliability
- **Context Migration = Rolling Update 4단계**: Connect → Duplicate & Shift → Consolidate → Steady state
- **K8s 대비 4가지 차별 속성**: Heterogeneity(이질성), Semantics(라우팅에 판단 필요), Sensitivity(민감도·규제), Learning(조직지능 축적)

## 실험·결과 요약
- **데이터**: 10인 컨설팅사 합성 시드(고객 3, 도메인 5, 파일 12), 정답 라벨 200 질의(sales 50, delivery 40, HR 30, finance 30, cross-domain 50).
- **정확성 실험 C1~C5**
  - C1 라우팅: 규칙 63.0% / LLM 75.0%(+12pp). 오분류는 "무관한 결과"일 뿐 "무단 결과"는 0 — 거버넌스가 라우터를 신뢰하지 않고 아래에서 필터링. 단 실용 가치엔 ≥90% 필요하다고 저자 판단.
  - C2 권한: 무단 전달 0, 오탐 0, 불변식 위반 0 (개발 중 Git 커넥터 cross-domain 누출 버그를 이 실험이 잡음).
  - C3 신선도: stale 0.65 ms, disconnect 0.02 ms, 20소스 사이클 23 ms.
  - C4 지연: 단일 도메인 81 ms, cross-domain 178 ms, 50 동시 에이전트 151 ms (직접 파일 읽기 0.01 ms). 오버헤드는 커넥터 I/O·의도분류가 지배.
  - C5 승인 격리: OTP 비노출, 오답 100회 거부, 재전송 공격 실패 등 8/8.
- **가치 실험 V1~V3**
  - V1 4개 베이스라인: B0 Ungoverned RAG(누출 375, 26.5%, noise 80.9%, 공격 0/5) / B1 ACL-filtered RAG(누출 0, noise 82.8%, 4/5) / B2 RBAC-aware RAG(295, 20.9%, 64.0%, 4/5) / B3 Context K8s(307, 20.9%, 64.0%, 5/5). LLM 라우팅 시 B3 noise 35.1%, 누출 161.
  - 해석: ACL 필터 = 누출 제거, 의도 라우팅 = noise 19pp 감소, 3-tier = 공격 전부 차단. B3가 모든 지표 1등은 아님(누출은 B1이 우수 — brokering으로 완전성↑ 대신 권한 표면↑).
  - V2 신선도 없을 때: 4개 시나리오 중 2개에서 phantom content 제공, "on track"/"at risk" 모순 동시 제공 → reconciliation 시 차단·최신본 우선.
  - V3 공격 5종: 무거버넌스 0/5, RBAC 4/5, CK8s 5/5. RBAC가 놓친 것 = "기밀 가격을 이메일로 발송"(역할은 이메일 권한이 있으므로).
- **형식 검증**: TLA+ TLC 4.6M 상태(33.6M 생성, 깊이 30)에서 S1 만료 콘텐츠 미제공, S2 Permission Engine 다운 시 fail-closed — 위반 0. Liveness는 테스트로만.

## 한계·미해결 과제
- 프로덕션 배포 없음, 합성 시드 데이터·단일 저자 설계·평가(벤더 조사도 문서 기반).
- 라우팅 정확도 75%는 실사용엔 부족(≥90% 필요 추정), LLM 라우팅은 +~1.4초 지연.
- **LLM-in-the-loop 긴장**: 거버넌스 보장 시스템이 확률적 라우터에 의존. 완화책(결정적 폴백, 분류 캐싱, 소형 특화 모델) 모두 트레이드오프 존재.
- 조직지능(R7)·Context Operator 미구현. Emergent sensitivity(개별은 무해, 패턴은 민감), 학습된 메모리 감사, 법적 discovery(FRCP), GDPR Art.22, NLRA 감시 이슈, EU AI Act 고위험 분류 가능성.
- 보안: context를 통한 prompt injection(목표 재프레이밍 38–40% 악용률 인용), 커넥터 침해, 부분결과로부터의 cross-domain 추론(side channel), operator 지식 오염. STRIDE/ATT&CK 위협모델 미작성.
- Alloy 권한 명세 미실행, liveness 형식검증 미완. Context unit 직렬화 표준(OCI 같은) 부재, 이질 타입 간 의미 정렬 미해결.
- 불변식은 mTLS, vault 자격증명, 미들웨어 무결성, LLM 제공자 DPA, 물리적으로 분리된 2FA 채널 전제 하에서만 성립.

## 기술 맵 관점 메모
- **"검색 품질" 축과 "거버넌스" 축을 분리**하라: 이 논문은 라우팅 정확도(relevance)와 권한 안전성(security)을 독립 계층으로 설계 — 맵에서 "무엇을 넣나"와 "넣어도 되나"를 다른 레이어로 배치.
- **K8s 유비 매핑표(Pod↔Context Unit, CRI↔CxRI, etcd↔Registry, Operator↔Context Operator)**는 컨텍스트 인프라를 "제어평면(control plane) vs 데이터평면(커넥터)" 구조로 정리하는 틀로 재사용 가능.
- 벤더 비교 축 후보: lock-in 수준, 승인 채널 격리(C1~C3), 정책 집행 위치(에이전트 코드 안/밖 — AWS Cedar), 신선도 관리 유무, 선언형 관리 유무.
- 선언형(Knowledge Architecture as Code) + reconciliation은 "기억·갱신" 단계의 핵심 기법 — 데이터 카탈로그(Collibra 등)·data mesh와 인접 영역으로 맵에서 연결.
- 프로토콜 계층(MCP/A2A = 전송) 위에 거버넌스·오케스트레이션 계층이 따로 있다는 층위 구분을 맵의 수직 스택으로 표현.
- 엔터프라이즈 데이터 플랫폼(Palantir/Snowflake/Databricks)은 이 문서에 없음 → 다른 소스에서 보완 필요; 이 문서는 "에이전트 플랫폼 벤더(MS/SF/AWS/Google)" 축의 근거로만 사용.
