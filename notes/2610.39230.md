# Beyond LLM Wrappers: Context Engineering and the Three-Engine Architecture for Reliable Financial AI (arXiv:2610.39230v1, 2026-10-29 제출 / 본문 표기 June 2026, Pradeep Kumar GS · Ravi Tanniru — Finteract AI)

## 한 줄 요약
재무 의사결정용 AI는 "LLM 래퍼"로는 불가능하며, **재무 지식그래프(기억) + 결정론적 최적화 엔진(계산) + 멀티에이전트 LLM(언어·검증)** 3개 엔진을 **context engineering 조정 레이어**(선택·순위·조합·검증·예산 배분)로 묶어야 한다는 실무형 아키텍처 논문. 15개 운영 배포(약 11개월)에서 환각률 7–9% → 1% 미만(관찰 증거)을 보고.

## 문서가 제시하는 분류 체계 / 아키텍처
- **요구사항 4종 (Section 2)** — 동시에 만족해야 하는 조건
  - 관계 기반 문맥 추론 — 단일 행이 아니라 벤더→송장→PO→입고→분쟁 같은 관계 경로가 답을 좌우
  - 결정론적 계산 — 같은 입력이면 같은 결과(재현성), 산술·최적화는 LLM에 맡기지 않음
  - 자연어 상호작용 — SQL/Cypher 없이 질문하고, 이의 제기 가능한 설명을 받음
  - 감사 가능성 — 데이터 계보·처리 출처·결정 근거·시간 유효성 보존
- **설계 원칙 5개** — 진실은 LLM 밖 구조화 시스템에 / 계산은 결정론 엔진에 / LLM은 해석·오케스트레이션·설명만 / 모든 답은 검증 가능 / 컨텍스트 조립을 1급 엔지니어링 문제로
- **3-엔진 아키텍처 (Section 3)**
  - 엔진1: 재무 Knowledge Graph — 기업의 장기 기억. 엔티티·관계·출처·시간 상태 저장
    - 멀티홉 추론 / 시간적 맥락(과거 상태·aging 전이) / 출처 귀속(ERP·레코드ID·sync 시각)
    - **LLM-aware 그래프 설계** — 사람이 읽기 쉬운 관계명(예: HAS_OPEN_INVOICE), 노드 요약·별칭·계층 포함
  - 엔진2: 결정론적 최적화 엔진 — 지급 스케줄·현금 배분·할인 포착 등을 solver(OR-Tools 주력)로 계산. "LLM은 무엇을 계산할지 정하고, 엔진이 계산한다"
  - 엔진3: 멀티에이전트 LLM 레이어 — 역할 분리된 5개 에이전트
    - Query analysis agent — 의도 분류, 엔티티·암묵적 기간 식별, 필요한 엔진 결정
    - Context assembly agent — 그래프 컨텍스트 검색, 탐색 깊이·필터 선택, 모델이 읽을 증거 준비
    - Optimization invocation agent — solver 입력(변수·제약·목적함수) 구성
    - Response generation agent — 사용자용 설명 생성
    - Validation agent — 생성된 주장을 그래프·solver 결과와 대조, 미지원 주장 제거/수정/에스컬레이션
  - 조정 레이어 = **Context Engineering** — 쿼리 분류, 엔티티 매핑, 탐색 전략, 시간·권한 필터, 계산 필요 여부, 컨텍스트 예산 배분, 검증 라우팅, 감사 기록
- **4층 감사 추적 (Figure 3)** — data lineage / process provenance / decision rationale / temporal validity
- **Context Engineering 구성 단계 (Section 4)**
  - 쿼리 이해 — lookup / explanation / optimization / scenario / hybrid 5유형 → 엔진 라우팅 결정
  - 엔티티 해석(entity resolution) — 별칭·약어·자회사 처리, 모호하면 불확실성 보존(조용히 틀린 벤더 선택 금지), 테넌트 범위·권한 준수
  - 서브그래프 선택 — 질문 유형별 다른 탐색 패턴, 너무 적으면 누락·너무 많으면 주의 분산
  - 시간 필터링 — 모든 사실에 유효 시점 부착, 서로 다른 시점 사실 혼합 방지
  - 테넌트 적응 — 산업·조직별 같은 용어의 다른 의미를 컨텍스트 템플릿 파라미터로 흡수
  - 예산 관리 — 쿼리/엔티티/그래프 사실/이력 요약/solver 입출력/검증 증거/정책/응답 지침 사이 공간 배분. "충분하되 최소"
  - 검증 — 엔티티·수치·시간·실현가능성·출처 주장 검사, 실패 시 수정·추가검색·명확화 질문·사람 검토
- **검증 6종 (Section 5)** — entity / numerical / temporal / constraint / source / feasibility validation
- **테넌트 차이 3수준** — schema(산업별 엔티티) / template(GST·VAT 등 규제) / instance(계정과목·승인 한도·명명 관행) → "parameterized reuse" 패턴
- **제안된 context engineering 벤치마크 4층** — ① 엔티티·관계 검색 정확성 ② 실행 계획 선택 정확성 ③ 주장 근거화(claim grounding) ④ context economy(최소 충분 컨텍스트 여부)

## 실험·결과 요약
- 대상: 150+ 고객 중 데이터 성숙도로 선별한 15개 운영 배포, 약 11개월, 제조·SaaS·서비스·이커머스·무역.
- 환각 측정: 약 500건 추천을 ERP 정답과 대조(엔지니어+재무 사용자+자동 검증). 하나라도 근거 없는 주장 있으면 환각으로 분류.
  - 단일 에이전트 파이프라인: 약 7–9%(쿼리 유형별 5–10%), 최적화 질의에서 더 높음(근거 없는 합계 생성).
  - 그래프 기반 멀티에이전트 검증: 사용자에게 도달한 미지원 주장 <1%. 남은 문제는 주로 검증 실패·누락 컨텍스트·데이터 품질 예외.
- 배포 기간: 초기 약 6주 → 재사용 자산 축적 후 약 2주.
- 정성 관찰: ERP 데이터 품질이 AI 모델링보다 더 많은 노력 소모 / 산업별 맥락이 중요 / 사용자는 추천보다 설명·추적성을 더 중시 / 사람 검토는 통제 장치로 유지 / **프롬프트 문구보다 컨텍스트 정책이 신뢰성에 더 큰 영향**.
- 사용 지표: hallucination rate, validation failure rate, entity resolution accuracy, solver feasibility rate, context sufficiency(비표준), time-to-go-live, user adoption.
- 주의: 무작위 대조 실험 아님, 성숙도·템플릿 개선·모델 업그레이드 등 교란 요인 존재.

## 한계·미해결 과제
- 관찰 증거 — 인과 주장 불가, 고객 선별 편향(데이터 성숙 기업 과대표집).
- 데이터 품질 의존 — 없는 원천 진실은 어떤 아키텍처도 만들어낼 수 없음.
- 공개 재현성 부족 — 사내 재무 데이터 비공개, 합성 데이터셋·재생 가능한 검증 트레이스 필요.
- 시스템 복잡도 — 저위험 요약·탐색에는 과잉.
- **Context 품질 지표 부재** — sufficiency, minimality, relevance, freshness, 테넌트 간 공정성 직접 측정 방법 없음. 컨텍스트 선택의 정식 최적화(관련도 함수 정의)도 미해결.
- 보안·프라이버시 — 테넌트 간 누출 없는 패턴 학습, 감사로그 민감정보, 데이터 레지던시.
- 모델 교체 시 행동 변화 모니터링 필요.
- 최적화 모델·그래프 스키마·검증 규칙의 정식 명세와 경제적 효과 정량화 미제공.
- 열린 질문: 누락된 핵심 컨텍스트를 생성 전에 감지하는 법, 탐색 깊이의 정확도-비용 최적화, 검증 실패 분류·학습.

## 기술 맵 관점 메모
- **"RAG vs Context Engineering" 축**: 텍스트 유사도 검색(RAG/GraphRAG) → 구조적 관련성(금액·긴급도·규제위험·관계 중요도·시간 상태)으로 확장되는 스펙트럼으로 배치 가능.
- **신뢰 원천 축(누가 사실을 말하나)**: LLM 내부 지식 ↔ 외부 구조화 원천(그래프/solver). 이 논문은 "사실·산술은 반드시 외부"라는 극단 — Palantir Ontology 류 "운영 온톨로지 + 액션" 계열과 같은 칸.
- **컨텍스트 = 데이터 + 실행계획**: context package와 execution plan을 함께 산출한다는 점에서, 맵에 "검색 레이어"와 "오케스트레이션/라우팅 레이어"를 분리 축으로 두는 근거.
- **사후 검증(validation) 단계를 파이프라인의 독립 노드로**: 생성 후 claim grounding 검증이 신뢰성의 핵심 레버 — 대부분의 일반 CE 문서가 약한 부분.
- **도메인 특화 vs 범용**: 테넌트 템플릿·산업 파라미터·권한 필터 → 엔터프라이즈 솔루션(Snowflake semantic views, Databricks Unity Catalog 등)과 연결되는 "거버넌스·멀티테넌시" 축.
- **평가 축**: 답변 정확도가 아닌 "컨텍스트 자체의 품질"(sufficiency/minimality/freshness/economy) 측정 — 맵의 평가 영역에 공백(open problem)으로 표시할 가치.
