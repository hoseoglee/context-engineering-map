# A Survey of Context Engineering for Large Language Models (arXiv:2507.13334v2, 2025-07-21, Mei·Yao·Ge 외 — 중국과학원 계산기술연구소(ICT, CAS) 중심, Guo·Liu 교신)

> 원문: `sources/papers/2507.13334.txt` (본문 약 2,900행 + 참고문헌 약 1,400편). 코드 저장소: github.com/Meirtz/Awesome-Context-Engineering

## 한 줄 요약
프롬프트 하나를 잘 쓰는 문제를 넘어, LLM에 들어가는 "정보 꾸러미(context)"를 여러 조각(지시·지식·도구·기억·상태·질의)으로 나누어 수집·가공·관리·조립하는 **시스템 최적화 분야**로 Context Engineering을 정의하고, 1,400편 이상의 논문을 "기초 구성요소 3개 + 시스템 구현 4개"로 분류한 서베이. 핵심 결론은 "모델은 복잡한 맥락을 *이해*하는 능력에 비해 그만큼 정교한 장문을 *생성*하는 능력이 크게 떨어진다(이해-생성 비대칭)"는 것.

### 핵심 정식화 (논문 §3.1)
- 기존 프롬프트 엔지니어링: `C = prompt` (고정 문자열 1개)
- 컨텍스트 엔지니어링: `C = A(c_instr, c_know, c_tools, c_mem, c_state, c_query)` — 조립 함수 A가 여러 조각을 형식화·연결
  - c_instr: 시스템 지시·규칙 / c_know: RAG·KG로 가져온 외부 지식 / c_tools: 도구 정의·시그니처 / c_mem: 이전 상호작용의 지속 정보 / c_state: 사용자·세계·멀티에이전트 상태 / c_query: 사용자 즉시 요청
- 목표: 과제 분포 전체에서 기대 보상을 최대화하는 함수 집합 F = {A, Retrieve, Select, …}를 찾는 최적화 문제, 제약은 `|C| ≤ L_max`(컨텍스트 길이 한계)
- 이론적 렌즈 3개: (1) 동적 컨텍스트 오케스트레이션(A = Concat ∘ Format들), (2) 정보이론적 최적 검색(정답과의 상호정보량 최대화 — "의미 유사"가 아니라 "최대한 유익한" 정보), (3) 베이지안 컨텍스트 추론(질의·이력·세계 상태가 주어졌을 때 최적 컨텍스트의 사후분포 추론)
- Table 1 비교 축: 모델 / 목표 / 복잡도 / 정보량 / **상태(stateless vs stateful)** / 확장성 / 오류 분석
- Context Scaling 두 차원: **길이 스케일링**(수천→수백만 토큰) + **멀티모달·구조 스케일링**(시간·공간·참여자 상태·의도·문화 맥락까지)

## 문서가 제시하는 분류 체계 (taxonomy)
(Figure 1 / Figure 3 / 목차 기준으로 재구성)

- **Context Engineering** — LLM 추론 시 주어지는 정보 꾸러미를 체계적으로 설계·최적화하는 분야
  - **Foundational Components (§4, 기초 구성요소)** — 어떤 시스템이든 쓰는 "부품" 수준의 기술
    - **Context Retrieval and Generation (§4.1)** — 맥락을 *만들거나 가져오는* 단계
      - Prompt Engineering and Context Generation (§4.1.1) — 지시문·예시·추론 틀(CoT 등)로 맥락을 직접 생성
        - Zero-/Few-shot & In-context Learning — 예시 유무·선택·순서로 과제 적응
        - Chain-of-Thought 계열(CoT, Zero-shot CoT, ToT, GoT) — 추론 과정을 단계·트리·그래프로 구조화
        - Cognitive Architecture Integration — 목표 명확화·분해·추상화 등 인지 연산을 프롬프트로 구현
      - External Knowledge Retrieval (§4.1.2) — 모델 밖 지식원(DB·KG·문서)에서 가져오기
        - RAG Fundamentals — 파라메트릭 지식 + 비파라메트릭 검색 지식 결합
        - Knowledge Graph Integration & Structured Retrieval — KG 트리플·경로·표에서 근거 수집
        - Agentic and Modular Retrieval — 에이전트가 검색을 계획·반성하며 수행 / 모듈 조립형 검색
      - Dynamic Context Assembly (§4.1.3) — 가져온 조각들을 하나의 맥락으로 *조립*
        - Assembly Functions & Orchestration — 템플릿·우선순위 선택·적응형 구성, 에이전트 선택·맥락 분배
        - Multi-Component Integration — 텍스트·구조·시계열·도구 인터페이스를 한 맥락에 통합(verbalization, 코드 표현)
        - Automated Assembly Optimization — APE·LM-BFF·Promptbreeder 등 자동 프롬프트 최적화
    - **Context Processing (§4.2)** — 가져온 맥락을 *변환·최적화*하는 단계
      - Long Context Processing (§4.2.1) — 아주 긴 입력을 다루는 기법
        - Architectural Innovations — SSM(Mamba), 팽창 어텐션(LongNet), TNN, 선형 어텐션
        - Position Interpolation & Context Extension — 위치 인덱스 재조정으로 창 확장(YaRN, LongRoPE, PoSE, Self-Extend)
        - Optimization Techniques — GQA, FlashAttention, Ring Attention, 희소 어텐션(S2-Attn, ESA, BigBird)
        - Memory Management & Context Compression — Rolling buffer, StreamingLLM, Infini-attention, H2O, InfLLM
      - Contextual Self-Refinement and Adaptation (§4.2.2) — 모델이 자기 출력을 다시 보고 고치기
        - Foundational Self-Refinement — Self-Refine, Reflexion, N-CRITICS, A2R, ISR-LLM
        - Meta-Learning & Autonomous Evolution — SELF, Self-rewarding, Creator, Self-Developing, meta-ICL
        - Memory-Augmented Adaptation — 문서를 메모리 뱅크에 압축 저장해 적응
        - Long CoT & Advanced Reasoning — o1/R1식 긴 추론과 그 압축(O1-Pruner 등)
      - Multimodal Context (§4.2.3) — 이미지·오디오·영상·3D를 맥락에 통합
        - Foundational / Advanced Integration — 인코더+정렬 모듈, 교차모달 어텐션, 계층 처리
        - Core Challenges — 모달리티 편향(텍스트 쏠림), 공간·시간 추론 부족
        - In-context & Long-context Learning — 이미지 토큰이 창을 많이 먹는 문제, 프레임 선택
      - Relational and Structured Context (§4.2.4) — 표·DB·KG 같은 구조 데이터 다루기
        - KG Embeddings & Neural Integration — GNN·GraphToken 등 구조를 벡터로
        - Verbalization & Structured Representations — 구조→자연어 문장 / 코드(Python, SQL) 표현
        - Integration Frameworks & Synergized Approaches — 사전학습 주입(K-BERT) vs 추론시 주입(KAPING) vs 양방향(GreaseLM, QA-GNN)
    - **Context Management (§4.3)** — 맥락을 *저장·조직·압축*하는 단계
      - Fundamental Constraints (§4.3.1) — 유한한 창, O(n²), lost-in-the-middle, 무상태성, overflow vs collapse
      - Memory Hierarchies and Storage Architectures (§4.3.2) — OS식 페이징(MemGPT, PagedAttention), 인지 원리 기반(MemoryBank, ReadAgent)
      - Context Compression (§4.3.3) — ICAE, RCC, kNN 메모리 캐시, 계층 KV 캐시(ACRE), 분산 KV(Infinite-LLM, KCache)
      - Applications (§4.3.4) — 문서 분석, 장기 추론, 멀티에이전트 상태 동기화, 장기 대화, 개인화 메모리
  - **System Implementations (§5, 시스템 구현)** — 부품을 조립한 실제 시스템 유형
    - **Retrieval-Augmented Generation (§5.1)** — 외부 지식을 생성에 붙이는 시스템
      - Modular RAG (§5.1.1) — 단계·하위모듈·연산단위 3계층으로 재구성 가능한 RAG
      - Agentic RAG (§5.1.2) — 에이전트가 계획·도구·반성으로 검색 전략을 동적으로 조정
      - Graph-Enhanced RAG (§5.1.3) — 문서 대신 엔티티·관계 그래프를 검색 단위로 사용(knowledge-based / index-based / hybrid GraphRAG)
      - Applications (§5.1.4) — 실시간·스트리밍 RAG, 동적 검색, 저지연, 증분 인덱싱
    - **Memory Systems (§5.2)** — 세션을 넘어 정보를 유지하는 시스템
      - Memory Architectures (§5.2.1) — 분류(감각/단기/장기; 파라메트릭/활성화/평문), 단기·장기 구현, 접근 패턴과 8대 메모리 연산
      - Memory-Enhanced Agents (§5.2.2) — 에이전트 아키텍처 통합, 실서비스(ChatGPT Memory 등), 메모리 기술 통합
      - Evaluation and Challenges (§5.2.3) — 지표, LongMemEval 등 벤치마크, 무상태성 한계, 최적화 방향
    - **Tool-Integrated Reasoning (§5.3)** — 텍스트 생성기 → 세계와 상호작용하는 행위자
      - Function Calling Mechanisms (§5.3.1) — 구조화 출력으로 외부 함수 호출, 학습 데이터·도구 선택 개선
      - Tool-Integrated Reasoning (§5.3.2) — 추론 중간에 도구를 끼워 넣기(프롬프트/SFT/RL 3방식, 단일도구→다중도구→에이전트)
      - Agent-Environment Interaction (§5.3.3) — RL 기반 도구 사용(ReTool, Search-R1), 평가(MCP-RADAR, GTA)
    - **Multi-Agent Systems (§5.4)** — 여러 에이전트의 협업
      - Communication Protocols (§5.4.1) — KQML/FIPA ACL → MCP·A2A·ACP·ANP, LLM 기반 통신 구조
      - Orchestration Mechanisms (§5.4.2) — 사전/사후·함수·컴포넌트·퍼펫티어·직렬화 오케스트레이션, 세션 기반 맥락 관리
      - Coordination Strategies (§5.4.3) — 트랜잭션 무결성(SagaLLM), 맥락 처리 실패, 에이전트 간 의존 불투명성
  - **Evaluation (§6)** — 맥락 공학 시스템을 어떻게 재는가
    - Evaluation Frameworks (§6.1) — 구성요소 수준(내재적) vs 시스템 통합 수준(외재적)
    - Benchmark Datasets (§6.2) — 기초 구성요소 벤치마크 / 시스템 구현 벤치마크(RAG·도구·웹 에이전트·MAS)
    - Evaluation Challenges & Emerging Paradigms (§6.3) — 방법론적 한계, 자기개선·비평가 기반 평가, 안전·강건성
  - **Future Directions & Open Challenges (§7)**
    - Foundational Research (§7.1) — 통합 이론, 스케일링 법칙·효율, 멀티모달 표현
    - Technical Innovation (§7.2) — 차세대 아키텍처, 추론·계획, 그래프 문제, 지능형 컨텍스트 조립
    - Application-Driven (§7.3) — 도메인 특화, 대규모 MAS 조정, 인간-AI 협업
    - Deployment & Societal Impact (§7.4) — 확장성·운영, 안전·보안, 윤리

## 저자가 꼽은 한계·미해결 과제
1. **이해-생성 비대칭(핵심 결론)**: 맥락 이해는 뛰어나지만 같은 수준의 장문·일관성 있는 출력 생성은 약함. 원인이 아키텍처·학습법·계산 한계 중 무엇인지 불명.
2. **통합 이론 부재**: 최적 컨텍스트 구성·중복 정량화·압축 한계를 다루는 수학적 틀이 없고, 현재 조립은 휴리스틱·도메인별 수작업에 의존. 구성요소 간 간섭·시너지의 형식 모델도 없음.
3. **O(n²) 확장 한계와 위치 편향**: lost-in-the-middle(중간 정보 접근 저하, 선행 맥락 있을 때 최대 73% 성능 저하), context overflow vs context collapse, KV 캐시 비대화.
4. **무상태성**: LLM은 본질적으로 상호작용마다 독립적이라 진정한 평생학습·누적 지식이 어렵고, 메모리 평가도 표준 벤치마크 부재 + 메모리 vs 추론 실패 원인 분리 불가.
5. **멀티모달·그래프**: 모달리티 편향(텍스트 쏠림), 세밀한 시공간 추론 부족, 그래프 구조를 언어 임베딩에 정렬하는 문제, 대규모·동적 그래프 일반화.
6. **도구·에이전트 성능 격차**: GAIA 인간 92% vs GPT-4 15%, GTA GPT-4 50% 미만. RL 도구학습은 정답만 보상해 도구 과의존(cognitive offloading) 우려.
7. **멀티에이전트 신뢰성**: LangGraph/AutoGen/CAMEL의 트랜잭션·보상 메커니즘 부족, LLM 자기검증에만 의존, 에이전트 간 가정 불일치, 중앙 오케스트레이터의 비결정적 실행 경로로 이상 탐지 어려움, 부분 실패 연쇄.
8. **평가 방법론**: BLEU/ROUGE/퍼플렉시티 부적합, 다구성요소 시스템의 실패 원인 귀속 곤란, "살아있는(living)" 벤치마크·장기 자율성·사회기술적·경제 지표 필요.
9. **보안·안전·윤리**: MCP/A2A/ACP 프로토콜 보안 취약점, 프롬프트 인젝션·데이터 오염·모델 추출, 메모리의 프라이버시(선택적 망각 필요), 명세 게이밍·보상 해킹, 편향, 투명성·감사 체계.
10. **운영(프로덕션)**: 지연·처리량·비용, 버전관리·하위호환·CI, 실시간 RAG의 증분 인덱싱과 스트리밍 데이터 정확도 저하.
11. 저자 스스로 빠르게 변하는 분야라 최신 연구 누락 가능성 인정.

## 기술 맵 관점 메모
- **조각(component) 축 = c_instr / c_know / c_tools / c_mem / c_state / c_query**: 논문의 정식화가 그대로 맵의 "무엇을 주입하나" 축으로 쓸 만함. 엔터프라이즈 제품(예: 시맨틱 레이어·카탈로그·온톨로지)은 주로 c_know·c_state를 공급하는 쪽으로 배치 가능.
- **파이프라인 축 = 생성·검색 → 가공 → 관리 → (시스템 구현)**: 3개 기초 구성요소가 사실상 수집/가공/저장 단계이고, 4개 시스템 구현(RAG·Memory·Tool·MAS)은 이 단계들을 가로지르는 "아키텍처 패턴"이라 2차원(단계 × 시스템 유형) 매트릭스로 배치하는 게 자연스러움.
- **개입 위치 축(모델 내부 vs 모델 밖)**: 같은 "컨텍스트 엔지니어링" 안에 아키텍처·학습 수정(Mamba, 위치 보간, FlashAttention, KV 축출, K-BERT, GraphGPT)과 순수 애플리케이션 계층(RAG, 프롬프트, 메모리 DB, MCP)이 섞여 있음. 엔터프라이즈 맵에서는 "모델 서빙/인프라 층 vs 애플리케이션/데이터 층"으로 분리해야 혼동이 없음.
- **표현 형식 축(자연어 vs 구조 vs 코드 vs 잠재벡터)**: verbalization, Python/SQL 표현, KG 임베딩, 토큰 수준 vs 잠재공간 메모리 구분이 반복 등장 — "어떤 형태로 넣나"를 별도 축으로 두면 GraphRAG·Text-to-SQL·시맨틱 레이어 제품 비교에 유용.
- **깔끔하게 안 들어가는 항목**: (1) Self-Refinement·자기진화 — 평가이자 가공이자 메모리 갱신이라 단계 횡단적; (2) Long CoT·추론 압축 — 모델 자체가 만드는 맥락(자기생성 컨텍스트); (3) 통신 프로토콜(MCP/A2A) — 도구 실행이자 거버넌스·상호운용 표준; (4) 트랜잭션 무결성(SagaLLM)·메모리 프라이버시·사용자 통제 메모리 — 논문은 평가/미래과제로만 다루지만 엔터프라이즈 맵에서는 별도 "거버넌스·권한" 층이 필요(논문에는 접근권한·데이터 계보·정책 기반 필터링 같은 거버넌스 기술이 거의 없음).
- **공백 지적**: 엔터프라이즈 데이터 플랫폼(Palantir 온톨로지, Snowflake/Databricks 시맨틱 레이어·카탈로그·권한 관리), 캐싱(prompt caching) 상용 기능, 관측성/트레이싱 도구가 서베이 범위 밖 — 다른 소스로 보완해야 함.
