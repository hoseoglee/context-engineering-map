# Agentic Context Engineering (ACE): Evolving Contexts for Self-Improving Language Models (arXiv 2510.04618, 2025-10 초판 / v3 2026-03-29, ICLR 2026, Zhang·Hu 외 — Stanford·SambaNova·UC Berkeley)

## 한 줄 요약
가중치를 바꾸지 않고 **context(시스템 프롬프트·에이전트 메모리)를 "계속 자라는 playbook"으로 다루는 방법**. Generator→Reflector→Curator 세 역할로 나누고, 컨텍스트 전체를 다시 쓰지 않고 bullet 단위로 조금씩 추가·수정(delta update)해서 brevity bias(짧게 줄이려는 경향)와 context collapse(통째 재작성 시 정보가 갑자기 사라짐)를 막는다. AppWorld +10.6%, 금융 +8.6%, adaptation 지연 평균 86.9% 감소.

## 문서가 제시하는 분류 체계 / 아키텍처
- **Context adaptation (= context engineering)** — 가중치 대신 입력(지시·전략·증거)을 고쳐서 모델 성능을 올리는 패러다임
  - 적용 대상 3종
    - System prompt — 다운스트림 작업을 안내하는 지시문
    - Memory — 과거 사실·경험을 다음 호출로 실어 나르는 저장소
    - Factual evidence — 환각을 줄이고 지식을 보충하는 근거 (RAG 등)
  - 적응 시점 2종
    - Offline adaptation — 학습 split으로 미리 프롬프트/playbook을 최적화 (예: system prompt optimization)
    - Online adaptation — 테스트 중 샘플 하나 풀 때마다 컨텍스트를 갱신 (test-time memory)
  - 기존 방법 계열 (natural-language feedback 기반)
    - Reflexion — 실패를 글로 반성해 다음 시도에 붙임
    - TextGrad — 텍스트 형태의 "gradient"로 프롬프트 최적화
    - GEPA — 실행 trace 기반 reflective prompt evolution + genetic Pareto 탐색
    - Dynamic Cheatsheet (DC) — 추론 중 전략·코드 조각을 외부 메모리에 누적 (단, 매번 통째 재작성)
    - MIPROv2 — 지시문과 demo를 Bayesian optimization으로 동시 최적화 (DSPy)
    - ICL — 예시를 프롬프트에 채워 넣기
  - 기존 방법의 두 가지 실패 양상
    - Brevity bias — 최적화가 짧고 일반적인 지시로 수렴해 도메인 세부 노하우를 버림
    - Context collapse — LLM이 누적 컨텍스트를 전부 다시 쓰다 갑자기 짧은 요약으로 붕괴
- **ACE 프레임워크**
  - 역할 분리 (agentic architecture)
    - Generator — 질의에 대한 reasoning trajectory를 만들고, 어떤 bullet이 도움/해가 됐는지 표시
    - Reflector — trace·실행 결과에서 구체적 교훈 추출 (최대 5회 반복 정제), bullet에 helpful/harmful/neutral 태그
    - Curator — 교훈을 작은 delta 항목(ADD 연산 JSON)으로 변환
    - 병합기 — LLM이 아닌 결정론적 로직으로 delta를 playbook에 merge
  - Context 표현: itemized bullets
    - metadata — 고유 ID + helpful/harmful 카운터
    - content — 재사용 전략·도메인 개념·흔한 실패 패턴 한 단위
    - 섹션 구분 — 예: strategies_and_hard_rules, apis_to_use..., verification_checklist, formulas_and_calculations
  - Incremental delta update — 전체 재작성 대신 국소 편집 → 국소화·세밀 검색·점진 적응, 병렬 merge 가능
  - Grow-and-refine — 새 bullet은 append, 기존은 in-place 갱신, 임베딩 유사도로 중복 제거; proactive(매 delta 후) 또는 lazy(윈도 초과 시)
  - Multi-epoch adaptation — 같은 학습 질의를 여러 번 재방문해 playbook 강화
  - Offline warmup → online — 오프라인으로 초기 playbook을 만든 뒤 온라인 적응 시작

## 기술 항목 카드
| 기술명 | 무엇을 하나(쉬운 말) | 파이프라인 단계 | 대표 방법·시스템 예시 | 근거 수치(있으면) |
|---|---|---|---|---|
| Evolving playbook (itemized context) | 컨텍스트를 한 덩어리 글이 아니라 ID 붙은 bullet 목록으로 관리 | 기억·갱신 / 조립·주입 | ACE playbook, A-MEM memory entry, DC cheatsheet | delta 없이 실행 시 AppWorld 평균 56.9 vs 70.3 (test-normal) |
| Incremental delta update | 바뀐 부분만 작은 조각으로 추가해서 기존 지식 보존 | 기억·갱신 | ACE Curator ADD 연산 + 비LLM merge | delta 제거 시 AppWorld test-normal TGC 76.2→67.3, SGC 64.3→46.4 |
| Grow-and-refine (dedup·pruning) | 계속 늘리되 비슷한 항목은 임베딩으로 합치고 오래된 건 정리 | 가공·압축 / 기억·갱신 | semantic embedding dedup, max context length 트리거 | dedup 50–90%, 프루닝 10K–100K 토큰 범위에서 성능 안정(77–78.6) |
| Reflector (성찰 분리) | 실행 결과를 보고 "무엇이 틀렸고 다음엔 어떻게"를 뽑아내는 전담 역할 | 평가 / 기억·갱신 | ACE Reflector, Reflexion, ExpeL | Reflector·multi-epoch 제거 시 59.4→55.1 |
| Bullet helpful/harmful 카운터 | 각 지식 조각이 실제로 도움됐는지 점수 매김 → 정리·필터 근거 | 평가 / 거버넌스 | ACE bullet metadata | — |
| 실행 피드백 기반 무라벨 적응 | 정답 없이 코드 실행 성공/실패 같은 환경 신호로 학습 | 평가 / 실행·도구 | ACE (GT 없음), DC | AppWorld 무라벨 +14.8% (offline) / +17.1% (online) |
| Multi-epoch / offline warmup | 같은 데이터를 여러 바퀴 돌리고, 오프라인으로 먼저 데운 뒤 온라인 투입 | 기억·갱신 | ACE | warmup 有 59.5 vs 無 56.1 |
| Reflective prompt evolution (비교 대상) | 프롬프트 후보 전체를 진화·선택 | 가공·압축 | GEPA, MIPROv2 (DSPy) | ACE가 GEPA 대비 지연 -82.3%, rollout -75.1% |
| Monolithic rewriting cheatsheet (비교 대상) | 메모리를 매번 통째로 다시 씀 → 붕괴 위험 | 기억·갱신 | Dynamic Cheatsheet (DC-CU/RS) | 18,282토큰→122토큰 붕괴, 정확도 66.7→57.1 (무적응 63.7보다 낮음) |
| KV cache / prompt caching | 긴 컨텍스트라도 반복되는 앞부분은 캐시 재사용해 비용 절감 | 조립·주입 (서빙) | Prompt Cache, CacheBlend, CacheGen, KIVI, InfiniGen, OpenAI prompt caching | 입력 토큰 91.8% 캐시 적중, 과금 입력비용 -82.6% (GPT-5.1) |
| Selective unlearning (논의) | 사람이 읽을 수 있는 컨텍스트라 특정 항목만 지워 개인정보·법규 대응 | 거버넌스·권한 | GDPR Art.17, CCPA 삭제권 언급 | 실험 없음(향후 과제) |

## 실험·결과 요약
- **설정**: Generator/Reflector/Curator 모두 DeepSeek-V3.1(non-thinking) 동일 모델(강한 모델 지식 전이 배제), batch 1, Reflector 정제 최대 5회, offline epoch 최대 5. 부록에서 GPT-OSS-120B, GPT-5.1, Llama-3.3-70B로 교차 검증.
- **AppWorld (agent, ReAct 기반, TGC/SGC)**: ReAct 42.4 → ACE offline 59.4(+17.0), 무라벨 57.2, online 59.5(+17.1). ICL 46.0, GEPA 46.4, DC 51.9. 리더보드(2025-09-20) 1위 IBM CUGA(GPT-4.1, 60.3)와 평균 동급, test-challenge에선 online ACE가 TGC +8.4%, SGC +0.7% 앞섬.
- **금융 (FiNER XBRL 139 엔티티 태깅 / Formula 수치추론)**: Base 69.1 → ACE offline 81.9(+12.8), MIPROv2 70.9, GEPA 72.5. Online ACE 76.6 vs DC 71.8. 무라벨에서는 FiNER가 오히려 떨어지기도(online 67.3) → 피드백 품질 의존.
- **기타 도메인**: DDXPlus(의료) 75.2→90.2(+15.0, GEPA +1.2). BIRD-SQL 47.8→52.9(+5.1, GEPA 52.2; Moderate/Challenging은 GEPA가 우세).
- **모델 일반화**: GPT-5.1 AppWorld online 54.2→65.8, GPT-OSS-120B 34.6→42.2. Llama-3.3-70B는 이득 작음(62.5→64.9). DC는 여러 모델에서 오히려 하락.
- **비용**: AppWorld offline에서 GEPA 대비 지연 53,898s→9,517s, rollout 1434→357, 입력 토큰 204M→39M(-80.8%). FiNER online에서 DC 대비 지연 -91.5%, 토큰비 $17.7→$2.9. 단, 평가 시 입력 토큰은 GEPA 대비 +117%(playbook이 길어서) — 캐시로 상쇄.
- **강건성**: 약한 Reflector(GPT-OSS-120B)로도 +5.9. 악성 Reflector를 매 iteration 넣을 때만 base 미만(66.7), 5회마다 1번이면 76.1로 여전히 상승.
- **하이퍼파라미터**: Reflection 3–5회가 적정, 10회는 과잉사고로 하락.

## 한계·미해결 과제
- **Reflector 품질 의존**: 교훈을 못 뽑으면 playbook이 노이즈·유해 항목으로 오염. 약한 모델일수록 이득 감소.
- **신뢰할 피드백 신호 필요**: 정답·실행결과가 없으면 ACE와 DC 모두 성능 하락 가능 (FiNER 무라벨 online -3.4).
- **긴 컨텍스트가 늘 좋은 건 아님**: HotPotQA처럼 짧은 상위 지시가 나은 작업, Game of 24처럼 규칙 하나면 되는 작업엔 과잉.
- **평가 시 토큰 증가**: playbook이 길어 raw 입력 토큰 2배 이상 — KV/prompt cache 인프라 전제.
- **Curator 연산이 사실상 ADD 위주**: 모순 감지·우선순위·오래된 항목 정리 등은 "호환 가능한 확장"으로만 언급.
- 향후: online/continual learning 대체, 선택적 unlearning(프라이버시·법규) — 아직 실험 없음.

## 기술 맵 관점 메모
- **"컨텍스트 = 학습 대상"축**: weight update(fine-tuning) ↔ context update(prompt optimization / memory / playbook). ACE는 "context-as-learnable-artifact" 노드로, GEPA·MIPROv2(프롬프트 최적화)와 DC·Reflexion(메모리 누적) 사이를 잇는 위치.
- **갱신 방식 축**: monolithic rewrite(요약·재작성) vs incremental delta(항목 단위 append/merge). 엔터프라이즈 지식베이스·CDC(change data capture) 패턴과 직접 대응시킬 수 있는 축.
- **피드백 신호 축**: GT 라벨 / 실행·환경 신호 / 무신호. 기업 환경에서는 "실행 로그·테스트 결과·사용자 승인"이 이 역할 → 평가·관측(observability) 레이어와 연결.
- **역할 분해 축**: Generator–Reflector–Curator 3역할은 컨텍스트 파이프라인의 "생성·평가·큐레이션" 단계에 그대로 매핑 가능 (기술 맵의 기억·갱신 단계 내부 구조).
- **서빙 비용 축**: 긴 컨텍스트의 비용은 KV cache/prompt caching으로 상쇄 → 컨텍스트 엔지니어링 맵에 "서빙 인프라(캐시)" 하위 노드 필요.
- **거버넌스 축**: 사람이 읽을 수 있는 bullet + helpful/harmful 카운터 = 감사·삭제가 가능한 컨텍스트 → 권한·unlearning 노드와 연결.
