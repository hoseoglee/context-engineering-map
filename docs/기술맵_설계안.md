# 컨텍스트 엔지니어링 기술 맵 — 설계안 (v0.1, 2026-11-11)

> 8개 자료(`../notes/`)를 모두 읽고, **기술을 어떻게 나누고 어떤 그림으로 그릴지** 정리한 설계 문서.
> 아직 맵 자체가 아니라 *맵의 뼈대*다.

---

## 0. 결론 먼저

**데이터는 하나, 그림은 여러 장.**

기술 하나하나를 "카드"(노드)로 만들고, 각 카드에 7가지 속성 태그를 붙여 한 파일(`map/nodes.yaml`)에 모은다.
그다음 같은 데이터로 목적이 다른 그림 3장을 뽑는다.

| 그림 | 답하는 질문 | 모양 |
|---|---|---|
| **① 스택 맵** (메인) | "컨텍스트 기술 전체가 어떤 층으로 이루어져 있나?" | 아래에서 위로 쌓인 7개 층 + 양옆을 관통하는 2개 기둥 |
| **② 흐름 맵** | "정보가 AI에 들어가서 결과가 나오기까지 어떤 단계를 거치나?" | 왼쪽→오른쪽 파이프라인 + 되돌아오는 학습 루프 |
| **③ 기업 포지셔닝 맵** | "팔란티어·Snowflake·Databricks·AI 회사는 각각 어디를 잡고 있나?" | 층별 커버리지 히트맵 + 2축 산점도 |

왜 이렇게 하나:
- 8개 문서가 제안한 분류 축을 세어 보면 **12개가 넘는다**(층, 단계, 주입 대상, 시점, 표현 형식, 제어 주체, 성숙도…). 한 장에 다 넣으면 아무도 못 읽는다.
- 축 하나를 골라 한 장만 그리면, 다른 축으로 보고 싶을 때 처음부터 다시 그려야 한다.
- 카드에 속성을 달아 두면 **그림은 필터만 바꿔 다시 뽑으면 된다.** 새 논문이 나와도 카드만 추가하면 된다.

## 2. 그림 ① 스택 맵 (메인) — 7개 층 + 2개 기둥

비유하면 **"회사 지식을 AI에게 건네는 공급망 건물"** 이다. 아래층일수록 원재료, 위층일수록 AI가 실제로 쓰는 형태다.

```
 ┌───────┬──────────────────────────────────────────────────────────┬────────┐
 │       │ L7 실행·검증   도구/액션 호출 · 결정론 계산엔진 · 출력 검증       │        │
 │       ├──────────────────────────────────────────────────────────┤        │
 │       │ L6 런타임 창 관리   조립 · 토큰 예산 · 압축 · JIT 검색 · 서브에이전트 │        │
 │  거   ├──────────────────────────────────────────────────────────┤  관   │
 │  버   │ L5 기억·이력   에피소드 기억 · 결정/이벤트 기억 · 출처(provenance)  │  측   │
 │  넌   ├──────────────────────────────────────────────────────────┤  ·   │
 │  스   │ L4 절차·역할   플레이북 · 역할 온톨로지 · 승인 체인 · 진화형 지침   │  평   │
 │  ·   ├──────────────────────────────────────────────────────────┤  가   │
 │  권   │ L3 관계·정체성   온톨로지 · 지식그래프 · ID 매핑 · GraphRAG       │        │
 │  한   ├──────────────────────────────────────────────────────────┤        │
 │       │ L2 의미(지표)   시맨틱 뷰 · 메트릭 뷰 · 시맨틱 레이어 · OSI 표준   │        │
 │       ├──────────────────────────────────────────────────────────┤        │
 │       │ L1 연결·원천   커넥터 · MCP/A2A(전송) · 벡터/문서 저장소 · ERP·DW │        │
 └───────┴──────────────────────────────────────────────────────────┴────────┘
   (접힌 띠) L0 모델·서빙 기반 — 긴 문맥 아키텍처, KV 캐시, 프롬프트 캐싱
```

| 층 | 쉬운 설명 | 대표 기술 (자료) |
|---|---|---|
| L1 연결·원천 | 데이터가 있는 곳과 AI를 잇는 배관 | CxRI 어댑터(Context K8s), MCP·A2A(서베이), 벡터 저장소(메모리 서베이) |
| L2 의미(지표) | "매출"이 정확히 뭔지 정해 둔 사전 | Semantic views(Snowflake), 분석 시맨틱 모델 |
| L3 관계·정체성 | "이 고객 = 저 시스템의 그 고객", 무엇이 무엇과 연결되나 | 관계·정체성 층(Snowflake), Domain 온톨로지(FAOS), 재무 KG(2610), Graph-Enhanced RAG(서베이) |
| L4 절차·역할 | "이런 질문엔 이 순서로, 이 사람이 승인" | Operational playbook(Snowflake), Role·Interaction 온톨로지(FAOS), ACE 플레이북 |
| L5 기억·이력 | "왜 이렇게 됐지?"에 답할 기록 | Event & decision memory(Snowflake), 4층 감사추적(2610), 에피소드/의미/절차 기억(메모리 서베이), 구조화 노트(Anthropic) |
| L6 런타임 창 관리 | 지금 이 질문에 무엇을 얼마나 넣을지 고르고 정리 | Context assembly agent·예산 관리(2610), Context Router·Endpoint(Context K8s), compaction·JIT·서브에이전트(Anthropic), 우선순위 절단(FAOS) |
| L7 실행·검증 | AI 답을 계산·실행으로 옮기고, 틀린 주장을 걸러냄 | 결정론 최적화 엔진·6종 검증(2610), 출력 검증 L4(FAOS), Function calling(서베이) |
| 기둥 A 거버넌스·권한 | 모든 층에 걸쳐 "넣어도 되나, 해도 되나" | 3-tier 승인·Permission Engine(Context K8s), Policy & entitlements(Snowflake), 테넌트 격리(FAOS) |
| 기둥 B 관측·평가 | 모든 층이 잘 돌아가는지 측정 | 4층 지표(메모리 서베이), 컨텍스트 품질 벤치마크 4층(2610), Freshness Manager(Context K8s) |

**설계 판단 3가지**
1. **L2(의미)와 L3(관계)를 나눈다.** Snowflake가 직접 이렇게 나눈다. 이걸 나눠야 Snowflake/Databricks(지표 중심)와 팔란티어(객체·관계·행동 중심)의 차이가 그림에 드러난다.
2. **거버넌스는 층이 아니라 기둥이다.** 권한은 원천에도, 기억에도, 실행에도 걸린다. 한 층에 넣으면 거짓 그림이 된다(Context K8s의 "검색 품질과 권한은 독립 계층" 주장).
3. **모델 내부 기술은 맨 아래 접힌 띠로 뺀다.** 서베이에 Mamba, FlashAttention 같은 기술이 섞여 있는데, 기업 솔루션 비교에는 거의 영향이 없다. 맵을 흐리지 않게 접어 둔다.

## 3. 그림 ② 흐름 맵 — 정보가 지나가는 길

```
 [수집·연결] → [정의·모델링] → [선별·검색] → [가공·압축] → [조립·주입] → [생성] → [실행·도구] → [검증]
                    ▲                                                                         │
                    └──────────────── [기억·갱신 / 학습 루프] ◀─────────────────────────────────┘
      ├──── 사전 큐레이션 구간 ────┤├──────── 런타임 구간 ────────┤        ├── 사후 구간 ──┤
          (FAOS: input-side)            (input/process-side)                  (output-side)
```

- 구간 3개는 FAOS의 결합 위치(입력/과정/출력)와 일치한다. **대부분 기업 시스템은 앞 구간만 강하고 뒤 구간(검증)이 비어 있다**(FAOS의 "비대칭 결합"). 그림에서 이 공백이 눈에 띄도록 한다.
- 되돌아오는 화살표가 ACE(진화형 플레이북)와 Snowflake 6단계 워크플로우("사용 로그로 컨텍스트를 개선")에 해당한다. 2026년 흐름의 핵심인 **"컨텍스트도 학습 대상"** 을 보여 주는 선이다.

## 4. 그림 ③ 기업 포지셔닝 맵

### ③-a 층별 커버리지 히트맵 (메인)
행 = 기업/제품, 열 = ① 스택의 층과 기둥, 칸 = ● 네이티브 / ◐ 부분·파트너 / ○ 없음 + **근거 등급**.

| | L1 | L2 의미 | L3 관계 | L4 절차 | L5 기억 | L6 창 관리 | L7 실행·검증 | 권한 | 관측 |
|---|---|---|---|---|---|---|---|---|---|
| Palantir (Ontology·AIP) | ● | ◐ | ● | ● | ◐ | ◐ | ● (Action) | ● | ◐ |
| Snowflake (Semantic views·Cortex) | ● | ● | ◐ | ◐ | ○ | ◐ | ◐ | ● | ◐ |
| Databricks (Unity Catalog·Genie) | ● | ● | ◐ | ○ | ○ | ◐ | ◐ | ● | ◐ |
| AI 회사 (Anthropic 등) | ◐ (MCP) | ○ | ○ | ◐ | ◐ | ● | ◐ | ◐ | ◐ |
| 에이전트 플랫폼 (MS·Salesforce·AWS·Google) | ● | ◐ | ◐ | ◐ | ◐ | ◐ | ● | ◐ | ◐ |

> ⚠️ **위 표는 자리만 보여 주는 가안이다.** 8개 자료 중 팔란티어·Databricks를 직접 다룬 것은 **0건**이다. 칸마다 공식 문서 근거를 채운 뒤 확정한다. 근거 없는 칸은 "추정"으로 흐리게 표시한다.

### ③-b 2축 산점도 (전략 지도)
- **X축: 컨텍스트의 성격** — 지표·분석 중심(숫자에 답함) ↔ 객체·행동 중심(업무를 실행함)
- **Y축: 컨텍스트를 누가 만드나** — 사람이 미리 큐레이션 ↔ 에이전트가 런타임에 스스로 찾음

```
            에이전트 런타임 자율
                    ▲
   AI 회사(Claude Code·JIT 검색) ●
                    │                     ● 에이전트 플랫폼
 지표·분석 ◀─────────┼─────────────────▶ 객체·행동
                    │
  Snowflake ●  ● Databricks              ● Palantir
                    │
            사람 사전 큐레이션
```

읽는 법: **오른쪽 위가 2026년 이후 모두가 향하는 곳**이다. Snowflake는 "AI가 컨텍스트를 만들고 사람이 승인"하는 방향으로 위쪽으로, 팔란티어는 AIP로 위쪽으로, AI 회사들은 MCP·메모리로 아래쪽(기업 지식)으로 움직이고 있다. 같은 그림 위에 **이동 화살표**를 그리면 동향이 한 장에 보인다.

### ③-c 성숙도 사다리 (보조)
FAOS의 L0~L5(무근거 → 주입 → 도구 필터 → 실행 게이트 → 출력 검증 → 폐루프)에 기업별 현재 위치를 찍는다. "누가 어디까지 왔나"를 한 줄로 보여 준다.

## 5. 카드(노드) 스키마 — `map/nodes.yaml`

```yaml
- id: ace-playbook
  name: ACE 진화형 플레이북
  plain: "일하면서 배운 요령을 항목 단위로 조금씩 쌓아 가는 지침서"
  layer: L4            # L0~L7 | gov | obs
  stage: memory_update # collect|model|retrieve|process|assemble|generate|execute|validate|memory_update
  coupling: process    # input|process|output
  injects: [c_instr, c_mem]   # 서베이 6조각
  timing: online       # preload|jit|hybrid|online|offline
  form: natural_language      # natural_language|structured|code|vector
  control: prompted    # heuristic|prompted|learned
  vendors: []          # 이 기술을 제품화한 곳 (근거 있을 때만)
  evidence: {level: A, src: "2510.04618", metric: "AppWorld +10.6%"}
  related: [dynamic-cheatsheet, reflexion, gepa]
```

```yaml
# 엣지(관계)도 따로 둔다 — 그림 ②의 화살표, ①의 층간 연결
- {from: semantic-views, to: ontology-identity, type: complements}
- {from: ace-playbook, to: dynamic-cheatsheet, type: improves_on}
```

- 근거 등급: A 동료심사 논문 / B 1차 공식 자료 / C 2차 해설 / D 추정. 그림에서 투명도로 표현한다.
- 렌더링: 처음엔 Mermaid(GitHub에서 바로 보임)로 그리고, 커지면 D3로 확대·필터가 되는 인터랙티브 페이지로 만든다. 같은 YAML을 읽는다.

## 7. 진행 순서 제안

1. **카드 만들기**: 8개 노트의 "기술 항목 카드" 표(합계 약 150행)를 스키마에 맞춰 `nodes.yaml`로 옮기고 중복을 합친다. 예상 60~90개 카드.
2. **공백 채우기**: 6절 자료 5~8건을 추가로 받아 같은 형식의 노트를 만들고 vendor 칸을 근거로 채운다.
3. **그림 ①②**를 Mermaid로 먼저 그린다. 기술 맵 본체.
4. **그림 ③** 히트맵과 산점도를 그린다. 기업 비교.
5. 인터랙티브 페이지(필터: 층/단계/기업/근거 등급)로 만든다.
